# Patent Agent V2-P1 Architecture

## Scope

V2-P1 upgrades the grounded generator into a human-in-the-loop patent engineering system. The V1/V2-P0 Document Engine remains frozen: Equation Engine, OMML, DOCX Renderer, Figure Renderer and Word COM are reused without redesign.

## Real Case Security

Real cases live under `workspace/private_cases/<CASE_ID>/`, which is Git-ignored. A case is created only through `real-case-create --authorized`; material is copied only from an explicit `real-case-ingest CASE PATH`. The system never scans desktop or research folders.

`real_case_manifest.json` records confidentiality, processing authorization, case LLM policy, external approval, source hashes, current checkpoint and case state. Effective LLM permission is the strict intersection of global and case policy:

```text
global disabled OR case disabled                    -> disabled
global local AND case local                         -> local
global external-approved AND case external-approved
  AND external_llm_approved=true                    -> external-approved
all ambiguous combinations                          -> disabled
```

Source paths are represented by filename and SHA-256 in the manifest. API keys and full source content never enter audit logs.

## Human Review Data Flow

```text
Evidence + AI/Deterministic Output
              |
              v
       Checkpoint Review Bundle
              |
              v
       Pydantic ReviewImport
              |
              v
 HumanCorrection + RevisionNode + Human Audit
              |
              v
 Human-confirmed/locked Knowledge
              |
              v
 Dependency invalidation (STALE, no eager rewrite)
              |
              v
 Minimal downstream regeneration
```

Source facts remain distinct from inventor assertions and human-confirmed facts. An edited sentence retains its old Evidence IDs only as partial provenance; it stays `SOURCE_FACT` only when the edited semantics are almost completely supported by those sources. Otherwise it becomes `HUMAN_CONFIRMED`.

## Revision and Locking

Every human operation stores a `HumanCorrection`. Important objects receive immutable `RevisionNode` versions with `previous_version_id`. The human audit stores actor, action, target, timestamp and content hash, not full technical text.

`human_modified=true` and `locked=true` prevent later generation from overwriting the value. Unlocking requires an explicit `UNLOCK` correction.

## Dependency Graph

```text
Evidence -> Fact -> Knowledge -> Candidate -> Strategy
         -> Claim Feature -> Claim -> Support/Scope/Traceability
Strategy -> Disclosure -> Figure/Traceability
Terminology -> Disclosure/Claim/Figure
Equation -> Disclosure/Traceability
```

A correction produces `change_impact_report.md` and marks affected artifacts `STALE`. Locked downstream artifacts remain locked. Recalculation is stage-specific: A1 reruns invention mining, B reruns disclosure/claim features, and C rerenders only affected Claims/support/scope.

## Checkpoint State Machine

Checkpoint state:

```text
NOT_STARTED -> GENERATED -> UNDER_REVIEW
UNDER_REVIEW -> CHANGES_REQUIRED -> UNDER_REVIEW
UNDER_REVIEW/CHANGES_REQUIRED -> APPROVED
GENERATED/UNDER_REVIEW -> BLOCKED -> UNDER_REVIEW
```

Case order is mandatory:

```text
INGESTED -> A1_REVIEW -> A2_REVIEW -> PRIOR_ART -> B_REVIEW
         -> DRAFTING -> C_REVIEW -> FINAL_RENDER -> VALIDATED
```

A checkpoint cannot be approved until every required object is reviewed. P0 questions block B/C. A scope warning (`VERY_NARROW`, or `VERY_BROAD` plus enablement risk) requires explicit acknowledgement. Real cases reject auto-approval.

## Checkpoint Responsibilities

- A1: technical field/problem, facts, components, steps, parameters, equations, effects, experiments and uncertainty.
- A2: candidate approve/reject/edit/merge/split/rerank.
- B: inventive concept, mandatory/dependent features, broad/balanced/conservative choice, terminology, support gaps and risks.
- C: Claim text plus feature graph, parent, support, Evidence, disclosure support, novelty and scope risks. Feature edits rerender Claim text and refresh support/scope.

## Claim Scope Review

Scope is deterministic-first. It combines feature count, strategy core, novelty matrix, support matrix, parameter usage and terminology registry. Rules detect:

- `PARAMETER_LOCKING_RISK` for unnecessary numerical limits;
- `IMPLEMENTATION_NARROWING` for concrete model/chip/controller limits;
- `ENABLEMENT_RISK` for missing core features;
- `SUPPORT_SCOPE_RISK` for scope beyond disclosure support;
- `NOVELTY_RISK` when imported prior art discloses the broad feature set.

Broad, Balanced and Conservative versions are rendered from the same feature pool. Manual long-sentence edits mark the structured mapping stale until reconciled.

## Evaluation Framework

Each `evaluation_runs/RUN-*` directory contains an immutable input snapshot and scorecard. Snapshot fields include Evidence hash, schema/prompt versions, provider, model, temperature and checkpoint starting state. Metrics include fact accept/minor/major/reject/omission, candidate proxies, Claim feature acceptance, unsupported features, narrowing/missing-core rates, correction count, calls, tokens and cost.

Model comparison is valid only when Evidence snapshot, prompts, schema and starting state match. Real data may be sent to a model only when that run independently satisfies the case policy.

## Security Boundary

V2-P1 deliberately excludes automatic CNIPA/PQAI search, vector databases, SaaS, multi-user authorization, cloud storage and patent filing. Generated Claims remain review drafts, not legal opinions.
